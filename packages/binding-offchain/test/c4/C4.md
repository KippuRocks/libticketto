# C4 — the offchain wire protocol, version 0

**Contract:** `C4`, between `binding-offchain` (`F-007`, in `libticketto`) and this
service (`F-010`). **Owner:** `F-010`. **Task:** `T-010-02`.
**Status:** agreed at `M0`. After that, changes go through `F-010`'s plan
(`PLAN.md` §2.2).

C4 is private. No party but `binding-offchain` speaks it, and nothing in it
reaches the SDK surface: the binding translates every response into the `C8`
port's values (`REQ-SDK-1`, `REQ-SDK-2`). The test vectors in
[`vectors/c4-v0.json`](vectors/c4-v0.json) are part of this contract. Where
they and this document disagree, both are wrong, and the disagreement is a bug.

The words MUST, SHOULD and MAY are used as RFC 2119 defines them.

## 1. Conventions

### 1.1 Versioning

Every endpoint of this version sits under `/v0`. Within `/v0`:

- The service MAY add fields to response bodies. The binding MUST ignore
  response fields it does not know.
- The service MUST refuse a request field it does not know (`malformed`, §4.2),
  so that a defect in either party is found rather than silently dropped. A new
  optional request field is introduced by deploying a service that accepts it
  before any binding sends it.
- Anything else — removing or renaming a field, changing a status code, a byte
  format or the meaning of a code — is a new version, `/v1`, served alongside
  `/v0` until no binding uses it.

The operational endpoint `GET /health` is not part of C4 and sits outside every
version prefix.

### 1.2 Bodies

Requests with a body, and every response except the hint stream (§3.5), are
JSON (`application/json; charset=utf-8`). The service MUST refuse any other
request content type with `malformed`. Request bodies MUST NOT exceed 256 KiB.

Values are carried as follows:

| Value | On the wire |
|---|---|
| Canonical bytes — a signed input, a sponsorship, a checkpoint | Lower-case hexadecimal string, even length, no prefix. The empty string is zero bytes. Upper-case digits, a `0x` prefix, or an odd length are `malformed`. |
| Identifiers (`EventId`, `TicketId`, `AccountId`, `OperationId`, …) | The SDK's own form: lower-case hex of the profile's canonical bytes |
| `Timestamp`, `Count` | JSON number; a non-negative safe integer |
| `Cursor` | String, compared for equality only (§1.4) |
| SDK values (queries, their results, log records' metadata, the assurance declaration) | The SDK's own JSON shapes, unchanged. `Option<T>` is `T` or `null`, always present |

**Why hex in JSON, not binary bodies.** The binding runs on React Native as well
as Node, using `fetch` only (`F-007` §5), and binary request and response bodies
are unevenly supported there. Hex matches how the SDK already carries
identifiers. The signed bytes are exactly the profile's canonical encoding: JSON
frames them and never re-encodes them, so what the service verifies is what the
signer signed.

### 1.3 What the bytes are

C4 defines no byte format of its own. Every byte string it carries is defined
elsewhere:

| Field | Defined by | Decoded with (`@ticketto/profile-v0`) |
|---|---|---|
| A signed command | `C2` — the profile's signed-input framing (`REQ-CP-1`) | `decodeSignedCommand` |
| A signed access pass | `C2` — the profile's signed-input framing (`REQ-CP-1`, `AD-13`) | `decodeSignedAccessPass` |
| A sponsorship | `F-023` (`T-023-01`, `@kippurocks/sponsorship`), opaque to the SDK | Not decoded by C4 or the binding. The service verifies it (§5); the binding passes through what its `Sponsor` returned |
| A checkpoint | `C7` (`F-006`, `T-006-03`) | Not decoded by C4 or the binding. A reader decodes and verifies it with `@ticketto/log` (`decodeCheckpoint`, `verifyCheckpoint`) |

A signed access pass travels in the profile's signed-input framing
(`encodeSignedAccessPass`), not in the form presented at the gate
(`encodeSignedPass`); a gate re-frames what it scanned before submitting.

A `signedInput` object names which of the first two it holds:

```json
{ "kind": "command", "bytes": "<hex: the profile's signed command>" }
{ "kind": "pass",    "bytes": "<hex: the profile's signed access pass>" }
```

### 1.4 Cursors and submission tokens

A `Cursor` is the SDK's opaque log position. On the wire it is a string of at
most 128 characters from `A–Z a–z 0–9 . _ ~ -`, so that it is carried in a query
string without escaping. The empty string is `LOG_START`. Only the service
interprets a cursor; the binding compares cursors for equality only.

A **submission token** is a string of the same alphabet, 1 to 128 characters,
returned by `POST /v0/submit`. It names one submission's outcome (§3.2). Only the
service interprets it.

### 1.5 Authentication

C4 has no caller authentication in version 0. Reads are not access-controlled:
the log they expose is published anyway (`REQ-TM-3`). Writes are controlled by
what they carry — the signer's authorisation, checked by the rules (`AD-25`), and
a sponsorship, checked by the service (§5). The service MUST be served over TLS
in any deployment reachable from outside its host. Rate limiting at the
transport level is an operational concern of the deployment, outside C4.

## 3. Endpoint definitions

### 3.1 `POST /v0/submit`

Submits one signed input with the sponsorship relaying it (`REQ-SP-1`). The
service accepts it for recording and answers at once; the outcome is read with
§3.2.

**Request:**

```json
{
  "input": { "kind": "command" | "pass", "bytes": "<hex>" },
  "sponsorship": "<hex>" | null,
  "presentedAt": <Timestamp>
}
```

| Field | Rule |
|---|---|
| `input` | Required. A `signedInput` (§1.3) |
| `sponsorship` | Required member. `null` only when the binding was given none — the service then refuses with `sponsorship-missing`; it never records an unsponsored write (`F-010` §5.3) |
| `presentedAt` | **Required for a pass, and absent for a command.** When the gate observed the pass, in milliseconds since the Unix epoch. Attested by the submitter, and bounded — not trusted — by the rules (`SPEC.md` §7.E, `F-008` §5.2). Present on a command, or absent on a pass: `malformed` |

**Checks, in this order.** The order is observable, so it is fixed:

1. The body is C4 JSON of the shape above, with every byte string in
   lower-case hex → else `400 malformed`. Nothing of the profile has run yet.
2. `input.bytes` decodes with the profile's decoder for its `kind` → else `422`
   with the §10 code that decoder returns (§4.1): `ERR-InvalidAuthorisation` from
   `decodeSignedCommand`, `ERR-InvalidPass` from `decodeSignedAccessPass`. The
   profile decides what an undecodable input is, so it is an outcome, not a
   defect.
3. `sponsorship` is not `null` → else `403 sponsorship-missing`.
4. The sponsorship verifies, from a configured sponsor account, and is bound to
   this input's operation id — for a pass, its pass id — and to this input's
   digest → else `403 sponsorship-invalid`.
5. Accepted: `202`, for a new submission or an identical one already held.

Nothing in steps 1–4 runs the rules. Everything the rules decide — expiry,
replay, authorisation, and every check of `F-008` §5.2 — is the outcome read
through §3.2, including a malformed authorisation inside a decodable command
(`ERR-InvalidAuthorisation`).

**Response `202`:**

```json
{ "operationId": "<OperationId>", "submission": "<submission token>" }
```

`operationId` is the command envelope's operation id, or the pass's id — a pass's
operation id is its pass id (`AD-15`). The binding reports `submitted` with it.

**Idempotency (`REQ-CM-1`).** A submission is identified by its `input` bytes and,
for a pass, its `presentedAt`. The service MUST store each accepted submission's
token and outcome **durably** — surviving a restart — until at least the
operation's expiry: a command's `expiresAt`; for a pass, `notAfter` plus the
maximum recording lag (`F-008` §5.6), the window in which it can still be
recorded (`REQ-AP-3`). Until then, an
identical request MUST answer `202` with the same `operationId` and the same
`submission` token, and its long-poll MUST yield the stored outcome, whatever it
is. An identical request sent before the expiry therefore reaches the rules once,
however often it is sent.

**Deduplication never outlives the operation's expiry** (`F-010` §5.5). After
it, a stored outcome answers nothing, even while retention keeps it: an
identical request answers `202` with the same token, but reaches the rules, which
reject it — `ERR-OperationExpired` for a command (`F-008` §5.4),
`ERR-PassExpired` for a pass (`F-008` §5.2) — and that rejection becomes the
submission's outcome. Every backend then gives the same outcome to the same late replay
(`REQ-SDK-1`). *Changed after `T-010-05`: the stored outcome answered until
retention removed it; and a pass's window, briefly `notAfter`, was widened to
`notAfter` plus the maximum recording lag.*

That is what makes the binding's retries safe: it resends the request it first
sent, field for field (`F-007` §5), and gets the first attempt's outcome. It
matters most for a pass. The rules refuse a pass that is submitted again after it
was consumed, with `ERR-PassReplayed` (`AC-E1.4`); a network retry of the
submission that consumed it must see that submission's receipt, not the
refusal. Otherwise the refusal would raise a false "same pass at two gates" flag
(`REQ-OP-3`). A retry is answered from the store for as long as the pass can
still be recorded; after that, it reaches the rules, which answer
`ERR-PassExpired`, never `ERR-PassReplayed`.

A **different** input carrying an operation id that is already recorded also
answers `202`, with the same `operationId` and a **different** token. Its outcome
is the rules' — `rejected` with `ERR-OperationConflict` — and it is read through
its own token, so it can never be mistaken for the original's receipt.

### 3.2 `GET /v0/operations/{operationId}?submission={token}&wait={ms}`

Long-polls the outcome of one submission.

| Parameter | Rule |
|---|---|
| `operationId` | Path. The `operationId` from §3.1 |
| `submission` | Required. The token from §3.1 |
| `wait` | Optional. Milliseconds the service may hold the request, `0`–`30000`; default `25000`. Out of range, or not an integer: `malformed` |

The service answers **as soon as** the submission is settled or rejected. If it
is neither when `wait` elapses, the service answers `pending`, and the binding
polls again. `wait=0` answers immediately.

**Response `200`** — one of:

```json
{ "state": "pending" }
{ "state": "settled",  "receipt": { "operationId": "<OperationId>", "cursor": "<Cursor>" } }
{ "state": "rejected", "error": { "code": "<ERR-*>", "detail": "<text>" } }
```

`settled` and `rejected` mirror the SDK's `SubmissionState`: the binding reports
them unchanged. A settled receipt's `cursor` is the cursor of the log record the
write produced (`Receipt`, `NFR-11`). A rejection's `code` is carried verbatim
from the rules (§4.1); `detail` is optional.

**Response `500`, with no C4 body** — the rules threw on this submission: a defect
of the service, not a ledger outcome. There is no wire code for it; the binding
treats it as a transport failure (§4.3), retries, and in the end reports
`ERR-LedgerUnavailable`. The service logs the defect and does not leave the
submission pending: an identical resubmission (§3.1) runs it again, and past
retention it is removed like any finished submission. *Ruled in `M1`
(`F-010` §5.5).*

**Response `404 operation-unknown`** — the service holds no submission for this
operation id and token: it was never accepted, its outcome is past retention, or
its outcome was produced before the operation's expiry and that expiry has passed
(§3.1).
The binding resubmits its identical request (§3.1), which is safe (`REQ-CM-1`).

**Retention.** The service MUST keep each outcome, durably and answerable here,
until at least the operation's expiry: a command's `expiresAt`; for a pass,
`notAfter` plus the maximum recording lag, the rules' consumed-pass retention
(§3.1, `F-008` §5.6). It MAY keep the row longer, but past the expiry the row is
no longer an answer, and an identical replay goes to the rules. The binding MUST therefore finish polling before the
expiry.

**Timeouts.** The binding SHOULD give each poll an HTTP timeout of `wait` plus at
least 10 seconds. A poll that times out, or fails in transport, is repeated — it
is a read, and changes nothing. `NFR-9` latencies up to about 60 seconds are
therefore two or three polls, and C4 sets no overall deadline: the binding's
retry budget does (§4.3).

### 3.3 `POST /v0/query`

Answers one point query (`REQ-MG-5`).

**Request:** the SDK's `Query`, unchanged:

```json
{ "kind": "getEvent", "event": "<EventId>" }
{ "kind": "getTicket", "ticket": "<TicketId>" }
{ "kind": "canAttend", "event": "<EventId>", "ticket": "<TicketId>" }
{ "kind": "getCancellationHolder", "ticket": "<TicketId>" }
{ "kind": "getCredential", "account": "<AccountId>", "credential": "<CredentialId>" }
```

Identifiers MUST be the profile's canonical form for their type: 32 bytes of
lower-case hex for `EventId`, `TicketId` and `AccountId`. A `CredentialId`'s
width depends on the credential's kind, so on the wire it is lower-case hex of
1 to 64 bytes. Anything else is `malformed`.

**Response `200`:** the SDK's `Result<QueryResult<Q>>`, unchanged:

```json
{ "result": { "ok": true,  "value": <QueryResults[kind]> } }
{ "result": { "ok": false, "error": { "code": "<ERR-*>", "detail": "<text>" } } }
```

| `kind` | `value` |
|---|---|
| `getEvent` | `Event` |
| `getTicket` | `Ticket` |
| `canAttend` | `AttendanceVerdict`. A refusal is a *value*, `{ "admit": false, "reason": "<ERR-*>" }` (`REQ-Q-3`), not an error |
| `getCancellationHolder` | `AccountId`, or `null` while the ticket's event is not cancelled |
| `getCredential` | `Registration`, as lower-case hex (§1.2): the registration that registered that credential to that account, or `null` when none did (`REQ-CP-6`). The account's other credentials stay unexposed (`REQ-MG-5`). *Added in `T-010-12`.* |

An error — `ERR-EventNotFound`, `ERR-TicketNotFound`, `ERR-PolicyUndeterminable` —
is carried verbatim (§4.1). Queries are side-effect free (`REQ-Q-1`) and safe to
retry.

### 3.4 `GET /v0/log?from={cursor}&limit={n}`

Reads the deployment's log in its total order (`REQ-SDK-5`, `AD-16`).

| Parameter | Rule |
|---|---|
| `from` | Required. A cursor; empty (`from=`) is `LOG_START`. A cursor this deployment never issued: `404 cursor-unknown` |
| `limit` | Required. An integer `1`–`1000`; anything else is `malformed` |

**Response `200`:** the SDK's `LogPage`, with each record's entry as a
`signedInput`:

```json
{
  "records": [
    {
      "cursor": "<Cursor>",
      "recordedAt": <Timestamp>,
      "event": { "id": "<EventId>", "sequence": <Count> } | null,
      "entry": { "kind": "command" | "pass", "bytes": "<hex>" },
      "presentedAt": <Timestamp> | null
    }
  ],
  "next": "<Cursor>"
}
```

- `records` are the records after `from`, in log order, at most `limit` of them.
  The service MAY return fewer, including none, without implying the end of the
  log. `next` is the last record's cursor, or `from` when there are none
  (`LogPage`).
- `event` is `null` for a write no event owns — registering a credential.
- `entry.bytes` is the signed input exactly as it was accepted. The binding
  decodes it with the profile into the SDK's `SignedCommand` or
  `SignedAccessPass`.
- `recordedAt` is by the ledger's clock (`REQ-SDK-3`).
- `presentedAt` is the time a pass's submitter claimed (§3.1), or `null` for a
  command. It is a claim the rules bounded, not a time the ledger observed.

Reading is authoritative; hints only say when to read (`AD-17`).

### 3.5 `GET /v0/log/hints`

A server-sent event stream (`text/event-stream`) telling readers that records
exist past a cursor. **It carries cursors only, never records** (`AD-17`).

```
event: hint
data: {"cursor":"<Cursor>"}

: keep-alive

```

- On connecting, the service sends one `hint` with the current head — the cursor
  of the latest record, or `""` when the log is empty.
- After that, it sends a `hint` when the head moves. It MAY coalesce several
  moves into one hint for the latest head, and MAY drop hints. A lost hint costs a
  reader latency, never data.
- It sends a comment line (`: keep-alive`) at least every 15 seconds while idle,
  so that intermediaries do not close an idle stream.
- Events carry no `id`, and the service ignores `Last-Event-ID`: a reader resumes
  by reading the log from its own cursor, not by replaying hints.
- The service MAY close the stream at any time. The binding reconnects with
  backoff; a reconnection's first hint re-establishes the head.

React Native bindings, which do not use this stream (`F-007` §5), poll §3.7's
`head` instead.

### 3.6 `GET /v0/assurance`

**Response `200`:**

```json
{ "assurance": { "INV-1": "enforced" | "attested", "…": "…" } }
```

The SDK's `AssuranceDeclaration`: exactly one entry for every invariant id the
SDK generates from `SPEC.md` §9, no other keys, each `"enforced"` or
`"attested"`. Its values for this service are §4.4's hosted column
(`T-010-07`): `INV-6` and `INV-7` enforced, every other invariant attested. The
vector carries those values, not a shape only.

The binding's value is the `assurance` member, not the whole body — as a
query's value is its `result` (§4.3). *Changed in `T-010-07`: the vectors'
`binding` value for this exchange was the whole body.*

### 3.7 `GET /v0/checkpoints/latest`

**Response `200`:**

```json
{
  "head": "<Cursor>",
  "checkpoint": { "cursor": "<Cursor>", "bytes": "<hex: C7 checkpoint>" } | null
}
```

- `head` is the cursor of the latest record, or `""` for an empty log — a cheap
  poll target for readers without the hint stream.
- `checkpoint` is the latest signed checkpoint (`REQ-TM-3`, `AD-16`): the cursor
  of the record it covers, and its `C7` bytes, which the binding does not decode.
  The bytes are a `C7` checkpoint — the sequence and hash of that record, signed
  with the publication key, a `p256` credential — and verify with `@ticketto/log`
  against that key's registration. `null` until the first checkpoint is
  published (`T-010-08`, `M5`).

## 4. Errors

C4 separates three things that must never be confused: an **outcome** the
ledger's rules decided, a **wire error** the service raised about the exchange
itself, and a **transport failure** in which the service said nothing usable.

### 4.1 Outcomes: `SPEC.md` §10 codes, verbatim

A rejection (§3.2), a query error (§3.3), and an input the profile refused to
decode at submission (§3.1 step 2) carry a §10 code exactly as the SDK spells it:

```json
{ "code": "ERR-PassReplayed", "detail": "pass already consumed" }
```

- `code` MUST be an error whose origin, in the SDK's generated
  `TICKETTO_ERROR_ORIGINS`, is `ledger`. Platform errors (`ERR-UnknownClass`,
  `ERR-ClassQuotaExceeded`) and binding errors (`ERR-LedgerUnavailable`,
  `ERR-SponsorshipRefused`) can never come from the service (`SPEC.md` §10, "Errors
  by where they arise").
- `detail` is optional, human-readable, and MUST NOT name a backend concept —
  no SQL state, table, transaction, host, or stack trace (`REQ-SDK-2`).
- The binding passes the code and detail through unchanged. A code that is not a
  ledger-origin §10 code is a protocol violation: the binding treats it as a
  defect (§4.3) and never passes it on.

An input refused at submission is answered:

```
422
{ "rejection": { "code": "ERR-InvalidAuthorisation" | "ERR-InvalidPass", "detail": "<text>" } }
```

### 4.2 Wire errors

Every non-2xx response from the service carries:

```json
{ "error": { "code": "<wire code>", "detail": "<text>" } }
```

except `422`, which carries a `rejection` (§4.1). `detail` is optional and, as in
§4.1, never names a backend concept. Wire codes are C4's own. They are
deliberately not §10 codes, and never reach the SDK surface as themselves.

| Status | Wire code | Raised when | Retry |
|---|---|---|---|
| `400` | `malformed` | The request is not C4, found before any signed input is decoded: bad JSON, an unknown or missing field, bad hex, an identifier of the wrong form, a parameter out of range, a wrong content type | No |
| `413` | `malformed` | The body exceeds 256 KiB | No |
| `404` | `not-found` | No such endpoint in this version | No |
| `404` | `operation-unknown` | §3.2: no retained submission for this operation id and token | Resubmit (§3.2) |
| `404` | `cursor-unknown` | §3.4: a cursor this deployment never issued | No |
| `403` | `sponsorship-missing` | §3.1: no sponsorship | No |
| `403` | `sponsorship-invalid` | §3.1: the sponsorship does not verify, is not from a configured sponsor, or is bound to another operation or another input | No |
| `503` | `unavailable` | The service cannot serve the request now — its store is unreachable, it is starting or draining. MAY carry `Retry-After` (seconds) | Yes |

### 4.3 Translation — what `binding-offchain` MUST do

Every response and failure falls in exactly one row. **An unmapped wire code, an
unexpected status, or a body that is not C4 is a defect** and fails loudly — in
tests and in production alike — rather than leaking (`F-007` §5).

| What the binding receives | What the SDK surface shows |
|---|---|
| `202` from §3.1 | `submitted` with `operationId`; then poll §3.2 |
| `200 pending` | Nothing new; poll again |
| `200 settled` | `settled` with the receipt |
| `200 rejected`, a ledger-origin code | `rejected` with that `TickettoError`, unchanged |
| `200` from §3.3 | The `Result` unchanged, its error a ledger-origin code |
| `200` from §3.4, §3.6, §3.7; a `hint` | The SDK value — the body of §3.4 and §3.7, the `assurance` member of §3.6 — after decoding each `entry` with the profile |
| `422 rejection`, a ledger-origin code | `rejected` with that `TickettoError` |
| `403 sponsorship-missing` | `rejected` with `ERR-SponsorshipRefused` |
| `403 sponsorship-invalid` | `rejected` with `ERR-SponsorshipRefused` |
| `404 operation-unknown` | Resubmit the identical request (§3.1); counts against the retry budget |
| `503 unavailable` | Retry with backoff, no sooner than `Retry-After`. Exhausted: `ERR-LedgerUnavailable` |
| **Transport failure** — no connection, DNS or TLS failure, reset, a timeout, or a `5xx` without a C4 `error` body (a proxy's `502` or `504`, say) | Retry with backoff. Exhausted: `ERR-LedgerUnavailable` |
| `400 malformed`, `413 malformed`, `404 not-found`, `404 cursor-unknown` | **Defect.** A submission fails (`SubmissionController.failed`); a read throws. Never retried; never mapped to a §10 code |
| A §10 code that is not ledger-origin; an unknown wire code; any other status; a `2xx` body that is not the shape above | **Defect**, as above |

Where the binding resubmits, it resends the request it first sent, field for
field, so the service's deduplication makes the retry safe (`REQ-CM-1`, §3.1).
Every read in C4 is side-effect free and may be retried freely. The retry budget
and backoff are the binding's (`F-007` §5), except that `Retry-After` is honoured.

`ERR-LedgerUnavailable` never appears on the wire. It is what the binding says
when the ledger cannot be reached (`SPEC.md` §10, amendment 0003 G8). No wire
code, status or detail carries a backend concept — block height, gas,
transaction hash, SQL state — into the SDK (`REQ-SDK-2`).

## 5. Sponsorship

Every submission carries a sponsorship; the service verifies it before the rules
run (§3.1 steps 3–4, `F-010` §5.3). Under `AD-18` A it is issued by Kippu's
sponsor relay (`F-023`), signed by a configured sponsor account, bound to the
submission's operation id or pass id and to the digest of its signed input, and
carrying a notional cost. C4 carries its bytes and does not define them: their
format and verification are `@kippurocks/sponsorship`'s (`T-023-01`), which the
service vendors from `kippu-api` and runs (`T-010-06`). The binding to the
input's digest stops a sponsorship for one input being attached to a different
input that reuses its id.

Stated plainly: because the service refuses unsponsored writes, a direct-path
write from Saifu or Iriguchi needs Kippu's relay to be up, even though this
service does not (`F-010` §5.3). That is accepted for the MVP backend only.

## 6. Test vectors

[`vectors/c4-v0.json`](vectors/c4-v0.json) holds one or more request–response
exchanges for every endpoint and every row of §4.3, among them a sponsored
command, a sponsored pass, an identical resubmission, a conflicting resubmission,
long-polls that settle, reject and stay pending, a log page, and a hint stream.

Each exchange records the HTTP request and response as sent, the SDK values its
byte strings decode to, and what `binding-offchain` surfaces (§4.3). Fields marked
`illustrative` — cursors, submission tokens, and the checkpoint — show shape
only: the service
chooses them, and a conforming implementation matches them for equality within
an exchange, not byte for byte.

The checkpoint is nonetheless real: its bytes are a `C7` checkpoint of the
vectors' own log — the record at its cursor in the log page, linked into `C7`'s
hash chain from the first record — signed with a software `p256` key listed
among the vectors' parties as `publication`. The suite decodes it and verifies it
with `@ticketto/log`, and checks that the hash it states is that record's.

The sponsorships are real too (`T-010-06`): issued with `@kippurocks/sponsorship` at
nil notional cost, each bound to its own input, and signed by a software stand-in
for the sponsor's KMS key, listed among the parties as `sponsor`. The service
under test is configured with that account. *Changed in `T-010-06`: they were
placeholder bytes.*

The vectors are generated by `test/c4/vectors.ts` from the real SDK, profile and
log packages, vendored from a pinned `libticketto` commit (`vendor/libticketto/`).
`pnpm test` fails when the checked-in file differs from what the generator
produces, and validates every exchange against this document with the profile's
and the sponsorship's codecs. Regenerate with `pnpm vectors:generate`.

## Appendix A. Test mode — not part of the production protocol

*Test mode, not part of the production protocol.* A service runs in test mode
only with `TICKETTO_TEST_MODE=1`, which it accepts only when
`TICKETTO_ENVIRONMENT` is `development` or `test`; in a `production` or
`staging` environment it refuses to start (`F-010` §5.5, `T-010-09`). No binding
may depend on anything here outside a conformance or test run.

In test mode, and only in test mode:

- **The ledger's clock is settable.** It moves only when told to, and never
  backwards (`REQ-SDK-3`). Every rule reads it, and so does retention.
- **Sponsorship verification is waived.** A `sponsorship` must still be present
  (§3.1 step 3), but its bytes are not verified (step 4), so a conformance run
  needs no sponsor relay (`REQ-SDK-9`). Verification itself is tested by the
  service's own suite.

Outside test mode the endpoints below do not exist: they answer
`404 not-found` (§4.2), like any path this version does not have.

### A.1 `GET /v0/testing/clock`

**Response `200`:** `{ "now": <Timestamp> }` — the ledger's current time.

### A.2 `POST /v0/testing/clock`

**Request:** exactly one of

```json
{ "set": <Timestamp> }
{ "advance": <non-negative integer, milliseconds> }
```

**Response `200`:** `{ "now": <Timestamp> }`, the time after the change.

A body that is not exactly one of these, a value that is not a non-negative
safe integer, or a `set` earlier than now (the clock is monotonic) is
`400 malformed`, and the clock does not move.

### A.3 `GET /v0/testing/config`

**Response `200`:**

```json
{ "maxRecordingLag": <ms>, "maxClockSkew": <ms>, "maxOperationLifetime": <ms>, "maxPassWindow": <ms> }
```

The limits the ledger's rules run with, in milliseconds (`F-008` §5.2, §5.4,
§5.6), so a conformance run can reach the edges they bound:

| Field | Bounds |
|---|---|
| `maxRecordingLag` | How long after a pass's `notAfter` it may still be recorded, and so how long a consumed pass id is kept — and how long an identical pass resubmission is answered from the store (§3.1) |
| `maxClockSkew` | How far ahead of the ledger's clock a pass's claimed `presentedAt` may lie |
| `maxPassWindow` | The longest window, `notAfter` − `notBefore`, a pass may carry; a longer one is `ERR-PassExpired` |
| `maxOperationLifetime` | How far ahead of the ledger's clock a command's `expiresAt` may lie |

These are the service's configured values (`TICKETTO_MAX_RECORDING_LAG_MS`,
`TICKETTO_MAX_CLOCK_SKEW_MS`, `TICKETTO_MAX_OPERATION_LIFETIME_MS`,
`TICKETTO_MAX_PASS_WINDOW_MS`; by default 5 minutes, 10 seconds, 24 hours and
5 minutes), read from the one object the rules are configured with. *Added for
M3; `maxPassWindow` added with `T-008-17`.*
